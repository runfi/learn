模型概念与 Personal Agent 全景

先理解模型如何生成，再分清信息、行动与结果由谁负责。用一张系统地图，把后续十三章放到正确位置。

第 01 章 / 01先看到完整系统，再认识模型

假设你对助手说：“参考我的学习偏好和明天的日程，安排半小时学习 Agent，创建前先让我确认。”一句话里同时包含语言理解、读取信息、作出选择、等待授权、改变外部世界和报告结果。模型只承担其中一部分。

本章要建立的判断：模型生成了什么，与系统实际做了什么，是两组需要分别检查的事实。Agent 是围绕模型构建的任务执行系统，由 Harness 组织上下文、调用模型、执行动作，并根据反馈持续推进目标。

本章先解释模型的输入与生成，再回到产品职责。第 02 章把一次对话展开为可追踪的过程，第 03 章再让这个过程根据工具反馈继续推进。后面的记忆、安全和恢复都在这张地图上增加能力，不另起一套故事。

第 01 章 / 02模型到底是什么：结构、参数与一次计算

模型结构（Architecture）定义计算如何连接；参数（Parameters / Weights）是训练得到的数值；推理（Inference）是给定输入后使用这些参数进行计算。参数不是一个能按用户 ID 查询的事实表，模型也不是在数据库中挑选一段现成答案。

容易混淆的对象它是什么不能由它直接推断什么
参数量可学习数值的规模指标；不同架构的激活计算量也可能不同不能单靠参数量判断你的任务准确率、延迟或成本
训练知识训练在参数中形成的统计规律和能力不保证记得某条记录的原文、出处或最新状态
上下文这次计算实际可利用的输入信息不是服务端保存的全部历史，更不是磁盘上所有文件
推理时中间状态计算产生的临时表示、缓存等不等于跨会话的个人长期记忆

Reasoning通常指推理、规划、检查等能力或过程；它和作为运行阶段的 Inference 不是同一维度。一次 Inference 可以产生简短回答，也可能包含较长的推理计算。更长输出、看起来像推理的解释，都不能单独证明过程正确。

从开发者角度，先问清三个问题：模型擅长什么任务，接口实际允许提供哪些信息，结果需要怎样核验。参数规模和模型类别是选型信息，任务上的真实表现才是设计依据。训练与推理的基本区分可参见 Hugging Face 的 Transformer 课程。

第 01 章 / 03从文字到计算：Token、Embedding、Attention

Token是模型编码和生成时使用的单位，可能对应一个词、词的一部分、汉字片段或其他符号。Tokenizer规定如何在文本与 Token ID 之间转换。不能把“一个汉字等于一个 Token”当作通则；不同 tokenizer 对同一句话的编码长度可能不同，特殊标记和消息封装也可能占额度。

Embedding把离散 ID 映射成数值向量，使后续网络能够计算。输入位置最初的 Token Embedding 与经过多层处理后的上下文表示应区分：同一个词在不同句子里的初始词项映射可以相同，但经过上下文计算后的表示会变化。第 07 章用于检索的整段文本向量是另一种应用，不能把所有 Embedding 都当成向量数据库记录。

Attention：从哪些位置取得信息

例如“我把笔记放进书包，它很重”，当前词的表示需要结合前文。Attention 根据表示间的匹配关系，对可见位置的信息加权组合；多头与多层可学习不同关系。它不是把某条数据库记录判定为真。

因果约束：不能偷看尚未生成的内容

常见自回归解码器在生成当前位置时只利用允许看到的前缀。网络还包含前馈变换、残差连接、归一化等组件；Attention 很关键，但不等于整个模型。

Transformer 原始论文给出了 Attention 与网络结构的基础。注意力权重不是可靠的“模型为什么这样决定”的完整解释，也不能直接用作答案真实性的置信度。

对 Personal Agent 的直接意义：上下文必须先进入模型计算才能起作用；更长输入会占用资源；格式和来源标签能帮助组织输入，却不等于强制模型正确使用。

第 01 章 / 04一句话如何逐步生成：预测、选择、追加

Logits是下一 Token 候选的未归一化分数。解码策略将分数转换或筛选，再选择一个 Token。于是“前面不同一个 Token，后面可能走向不同答案”：不仅单步随机选择会变，后续的条件本身也变了。

在常见实现中，Prefill处理已有输入，Decode继续生成；KV Cache复用已计算的注意力键和值，减少重复计算。缓存保存的是计算中间结果，不是用户画像，不保证刷新界面后任务能够继续。缓存机制见 Hugging Face 缓存说明；具体服务的调度、缓存命中和计费另按产品核实。

结束情况能够说明不能说明
自然停止或结束标记模型这次不再继续输出用户目标一定完成，或事实已核验
输出预算耗尽到达设置或服务允许的生成限制答案已经完整；结构化结果可能被截断
取消、错误或连接中断某个生成或传输阶段终止上游和外部工具都已停止，或未产生任何副作用

模型生成与界面展示是两件事。服务可以合并多个 Token 再发送，也可以将内容按其他边界发送。第 02 章会解释为什么 20 次增量事件不等于 20 个 Token。

第 01 章 / 05Temperature 改变分布，Top-k / Top-p 筛选候选

把下一步候选的基础概率设为 A：60%、B：30%、C：10%。这些数值表示在当前条件下生成哪个 Token 的概率，不是三个答案“正确”的概率。下面固定模型、输入与分数，只改变 Temperature；不叠加其他过滤。

常见定义为 logits 除以正数 T 再做 softmax。只记一个关系即可：

pi(T) = exp(zi / T) / Σj exp(zj / T)

这里 z 是 logits，T 是 Temperature。已知 T=1 的概率时，也可以用 pi1/T 再归一化计算上图。Temperature 本身通常不把某个候选硬删除；它改变概率集中程度。T 趋近 0 时概率集中到最高分候选。接口中的 T=0 往往对应特殊的贪心解码处理，不能把 0 直接代入公式。

参数它控制什么用当前三候选举例
Top-k保留概率最高的 k 个候选；k 是数量变量k=2 保留 A、B，删除 C，再归一化
Top-p / Nucleus sampling按概率降序取最小前缀，使累计概率达到或超过 p；p 表示概率阈值p=0.8：A 累计 0.6 不够，加 B 后 0.9 达标，保留 A、B
Temperature调整分布的集中程度，不是候选数量阈值T=0.5 时 A 约 78.3%；T=2 时 A 约 47.3%

参数含义参见 Transformers generation 文档。如果同时使用 Top-k 和 Top-p，先后顺序、重新归一化以及最小保留数取决于实现；不能把一种库的流水线当成所有模型 API 的标准。某些模型也不暴露这些参数。

你之前的类比可以修正为：Temperature 调整“偏爱第一名的程度”，Top-k / Top-p 调整“哪些候选有资格参与”。降低 Temperature 不代表模型增加了业务限制，高 Temperature 也不代表模型认为“什么都正确”。

不同模型对同一上下文给出的基础分数不同，即使使用相同 Temperature，最终分布和回答也可能不同。低 Temperature 能减少一部分采样变化，却不能保证事实正确，也不能独自保证跨模型版本、硬件和服务实现的逐字复现。

第 01 章 / 06模型实际拿到什么：消息、资料与权限边界

角色（Role）帮助接口区分消息来源；指令优先级是产品定义的行为规则；权限决定系统实际允许访问和执行什么。三者相关，但不能互相代替。写一句“你没有删除权限”，不等于操作系统或工具已经禁止删除。把恶意网页放在请求末尾，也不应让它自动取得高于应用规则的权限。

Harness 对输入的“可控”，具体意味着可以选择哪些资料进入、设置规则、划分来源和预算。它不是对模型行为的完全控制：模型仍可能误读，输入内容也可能相互冲突，所以关键行为需要程序检查和执行边界。指令作用范围、加载时机和压缩策略在第 05 章深入。

历史存在 ≠ 本轮看见

聊天数据库可以保存十万条消息，本轮却只选了其中一部分。判断回答依据要看实际请求，而不是看产品侧存了多少东西。

文件存在 ≠ 模型读取

笔记在磁盘或连接器里，只说明资料可被系统获取。需要读取、选择并提供给模型，内容才可能影响本轮回答。

多模态模型可以处理图片、音频等输入，因此“一次模型调用只是文字输入、文字输出”过于狭窄。文本模型常以 Token 工作，多模态还可能包含图像块、音频表示和专用标记，计数与能力按模型接口确认。本课程主要用文字案例研究系统机制，不假设图片路径本身就等于图片内容已送达。

第 01 章 / 07完整案例 B：回答像真的，还需要什么证据

固定请求：“根据我的学习笔记，解释 RAG 和长期记忆的区别，各给一个例子，并标明依据哪份笔记；资料没写到的就说明不知道。”本章把两份短笔记手工提供给模型，不假装系统已经实现了自动检索。

资料本章提供的教学内容可以支持的结论
N1 · 检索与回答先检索相关资料，再提供给模型用于生成；可用关键词、向量或混合检索RAG 描述一种借助检索信息生成回答的方法
N2 · 用户长期记忆保存需要跨会话使用的信息；产品负责保存、更新、读取和删除长期记忆描述跨会话保存和使用信息的机制

合理答案可以是：“查课程笔记再回答，是 RAG 的例子（N1）；下次会话仍能按保存的上午学习偏好安排，是长期记忆的例子（N2）。两者可以配合：记忆条目也能通过检索提供给生成过程。”前两句由笔记直接支持，最后一句是基于两种机制的关系说明，不应伪装为笔记中的逐字引用。

基准：提供 N1 + N2

检查两部分解释是否匹配、例子是否正确、引用能否定位。一次正确回答只说明这次表现，不代表总体稳定正确。

变体 B1：只移除 N2

其他条件不变。合理行为是说明笔记缺少长期记忆依据；模型可能凭参数知识知道答案，但不能把它说成来自未提供的 N2。

Grounding（依据约束）强调回答与指定资料的对应关系。核验要区分“世界上可能正确”与“被这次指定资料支持”：用户要基于私有笔记回答时，这个差别就是产品要求的一部分。第 07 章再学习如何选出资料；本章只把信息提供和证据检查分开。

第 01 章 / 08Chatbot、Workflow、Agent、Harness 与 Runtime

术语主要看什么日历例子
Chatbot对话式产品界面或交互形式；底层可以很简单，也可以有 Agent用户通过聊天提出安排学习的请求
Workflow主要步骤和分支由预先定义的流程组织，内部可以调用模型固定先查日历，再填候选表，确认后创建
Agent在约束内根据当前目标与环境反馈动态选择后续行动发现冲突后决定重新查询、提新候选或向用户澄清
Harness围绕模型组织上下文、工具、状态和控制的应用层机制将模型的创建提议送去校验，等待确认后才派发
Runtime承载任务执行的运行机制：进程、调度、生命周期等，具体边界随产品而异保持等待状态、处理取消、管理任务运行；不是大模型本身

这些不是五种互斥产品。一个聊天产品可以使用固定 Workflow，在某些步骤嵌入 Agent 决策，再由 Harness 和 Runtime 承载。术语在不同框架中有交叉；讨论架构时应说职责，不要仅凭组件名推断能力。

Anthropic 2024 年的架构文章用预定义流程与动态控制区分 Workflow / Agent，这里借用这一分析方式，不把它当成行业唯一术语标准，也不据此推断当前托管产品的实现。

Agent 的关键不是外层系统“庞大”，而是围绕目标形成受约束的决策—行动—反馈过程。只有日志和数据库的单次聊天服务，即使组件很多，也不因此自动具备 Agent 的动态行动能力。

第 01 章 / 09三种“成功”：生成成功、动作成功、任务成功

用户任务仅有一句话还缺什么需要的可核验事实
A · 记住偏好“我记住了”不能证明跨会话可用记录落盘，新会话按用户读取并使用，允许更正和删除
B · 根据笔记解释“根据你的笔记”不能证明读到了资料实际输入包含授权资料，结论由对应来源支持
C · 安排日程“已安排”不能证明外部世界发生变化确认绑定具体方案，创建有结果，时间、时区、时长与目标一致

同样要分开格式正确、语义正确、权限正确、执行成功。结构化输出让程序更容易解析，Schema 约束能检查字段形状；它们不能独立证明会议不冲突，也不能替用户作出授权。一个完全符合结构的“删除所有事件”仍可能是错误或未授权动作。

选择设计时看任务约束：仅解释公开概念，单次调用可能足够；固定资料审批，Workflow 容易控制；需要根据多种外部反馈不断调整的任务，才考虑 Agent 闭环。更多自主性会带来更多不可预测路径、观察需求和控制成本，应有具体收益来支持。

第 01 章 / 10总结、自述与参考答案

尝试不用术语堆砌回答三个问题：为什么模型说“记住”不等于真的记住？Temperature 与 Top-p 分别改变什么？你会在哪里检查日历真的创建成功？下面给出完整答法，供想过以后对照。

1. Agent 和一次模型调用差在哪？

Agent 是围绕模型构建的任务执行系统，由 Harness 组织上下文、调用模型、执行动作，并根据反馈持续推进目标。一次调用提供候选输出；Agent 还要决定是否继续、真正执行什么、如何检查结果以及何时结束。系统不一定庞大，关键是职责闭环。

2. 模型为什么知道很多，却不知道我的笔记？

训练让模型形成通用知识和语言能力，但私有笔记不一定在训练数据里，更不一定是最新版本。应用必须先获得读取权限，再把相关内容提供给本轮调用。即使模型猜中了答案，也不代表它读过那份笔记。

3. Temperature 可以理解成采样阈值吗？

不准确。Temperature 调整候选概率的集中程度，Top-k 和 Top-p 才直接筛选候选集合。把 T 调低会更偏向高分候选，但不能把事实错误变正确；换模型后基础分数不同，相同 T 也不会保证相同回答。

4. Top-p=0.8，累计达到 0.9 的那个候选会丢掉吗？

不会。按降序累加到达到或超过 0.8 的最小前缀，包括最后那个使总和越过阈值的候选。例如 0.6、0.3、0.1 保留前两个，总和 0.9，再在保留集合内归一化。

5. 上下文、长期记忆和参数知识怎么区别？

参数知识在训练后的模型数值中；上下文是这一次调用实际得到的信息；长期记忆是产品跨会话保存并按需取用的信息。长期记忆只有通过读取等路径进入当前可用输入，才可能影响本轮回答，它不是每聊一句就自动写入模型参数。

6. JSON 合法、引用存在，为什么仍可能错？

JSON 合法只保证可解析，引用存在只证明有那份资料。还要检查字段是否符合业务含义、引用是否支持对应结论，涉及行动时再检查授权和真实执行结果。这些是不同层次的验证。

7. 模拟生产面试：用户投诉“助手说已记住，下次却忘了”，怎么查？

【生产场景模拟，非真实项目经历】我会从一次具体请求查：系统是否识别保存意图，是否真的写入，记录属于哪个用户和范围；再查新会话有没有读取、有没有进入实际上下文。如果写入成功但没读入，是信息使用链的问题；如果仅生成“我记住了”，则保存链根本没完成。不同位置需要不同修复。

本章的自述主线：输入被编码并参与计算 → 解码策略形成输出 → Harness 解释输出并控制动作 → 系统用证据判断任务结果。下一章把这条线展开成一轮对话的时间与状态变化。
