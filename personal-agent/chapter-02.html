第 02 章 · 深入教材 · 理论阅读

一次对话、会话状态与基础追踪

沿着用户的一次发送，追踪输入、网络、生成、保存与状态。让“没回答、没记住、没保存”都能落到具体证据。

更新于 2026-11-18 · 图中案例为教学设定 · 阅读不自动代表掌握

第 02 章 / 01先确定边界：这次只完成一次有依据的对话

本章仍用任务 B：“根据我的学习笔记，解释 RAG 和长期记忆的区别，各给一个例子，并标明依据哪份笔记；资料没写到的就说明不知道。”N1/N2 由应用手工提供，偏好也是已给定的教学快照。这里没有自动检索、自动记忆或日历动作。

本章核心问题：同一句“没有回答”，可能是请求没有发出、会话无权访问、模型失败、传输断开，或生成成功但没有落盘。要定位它，必须知道每一层负责什么、保存什么、发出了什么证据。

一次模型响应可以分成许多片段，一轮用户对话可以包含重试，未来一个 Agent 任务还会跨越多轮。我们先把这些不同尺度的对象分清，再讨论网络和追踪。

第 02 章 / 02先分清对象：Session、Message、Turn、Attempt

标识解决的定位问题不应混用的对象
session_id这些消息属于哪段会话，谁可以访问不能代替用户身份和授权检查
turn_id这次用户提交产生了哪些尝试和结果不能用文本相同判断是同一轮
request_id这一条网络请求如何贯穿日志浏览器请求和供应商请求通常有不同 ID
attempt_id第几次实际调用，哪里重试过不同尝试不能覆盖成同一条成功日志
message_id具体展示或保存的是哪条内容不能把界面列表下标当稳定消息身份

为什么不只保存一串聊天文本？因为文本不能可靠表达“用户取消了”“第一次尝试失败，第二次成功”“答案仅输出一半”。这些是结构化执行事实，需要可查询的状态。聊天内容可以解释用户说了什么，执行记录解释系统做过什么。

本章的完成条件是：这轮响应过程有明确终态，并能知道哪份内容被保存。第 03 章的任务完成还要检查外部行动和用户目标，不能把 Turn 完成直接当作 Task 完成。

第 02 章 / 03从点击发送开始：前端分支与后端检查

前端负责输入体验，例如阻止空白提交、显示发送中、暂存草稿。后端负责可信校验：身份、会话归属、输入大小、状态是否允许提交。不能因为按钮在界面上被禁用，就认为另一个标签页或直接发来的请求也被阻止了。

服务端认可提交之后，应为这一轮建立可追踪身份，再记录用户消息并取得一致的历史视图。产品可选择“先保存消息，再开始模型调用”，这样模型失败仍能保留用户提交；也可用事务将相关状态一起落盘。关键是对外承诺与持久事实一致，而不是某一种表设计必须照抄。

发送失败

服务端可能完全没收到，也可能收到后响应丢失。因此重发需要稳定的提交标识与去重规则，不能仅比较用户文本。

会话繁忙

选择拒绝、排队或独立分支。无论哪种策略，都应让用户知道下一条消息会在什么历史基础上执行。

如果请求被拒绝，不能还在 UI 中伪装成“模型正在思考”。从开始就区分“正在提交”“已接受”“等待模型”，后面排障会容易得多。

第 02 章 / 04模型调用前：组装、校验与输入快照

数据契约（Contract）说明模块之间交换什么、字段意味着什么、哪些值有效，以及失败怎样表示。前端提交的原始内容、应用内部消息、供应商 API 的输入不一定具有相同结构，适配层负责转换，不应把供应商格式蔓延成所有业务对象。

检查层检查什么即使通过，仍可能有什么问题
请求形状类型、必填字段、长度、内容类型字符串可以合法但指向错误用户的会话
业务语义身份、归属、当前状态、允许的输入有权限提交，不代表请求中的笔记事实正确
模型接口契约支持的角色、模型参数、输入额度服务可能拒绝、限流、超时或返回不满足任务的内容
结果契约文本是否完整，结构是否可解析，字段是否有效格式正确的解释仍可能没有资料依据

请求快照至少应能回答：使用了哪个模型标识、哪版应用规则、哪些消息、哪版资料，以及重要调用设置。生产环境里快照可能包含私密信息，不能无条件全文写日志；可以采用受控存储、脱敏、摘要与内容版本引用。需要调试时能定位，权限和保留期限也要明确。

对于本章 B1，撤去 N2 之后若答案仍声称依据 N2，先查实际输入：历史里是否残留 N2，快照是否选错，还是模型真的编造引用。没有快照，单看最后答案往往分不清。

此处只建立“必须知道实际输入”的原则。信息筛选、预算分配、指令作用范围和压缩事务集中在第 05 章主讲，避免现在就引入整套上下文架构。

第 02 章 / 05流式到底流了什么：生成、字节、事件、界面

Streaming是结果可逐步交付的方式；SSE（Server-Sent Events）是通过 HTTP 传输事件流的一种格式与浏览器接口机制。它不是模型生成算法，也不是 WebSocket。SSE 流使用 UTF-8，事件由字段行构成，空行划分事件；具体格式见 WHATWG 标准。

浏览器原生 EventSource接口与“使用 fetch 发送请求后读取 SSE 格式的响应体”也要区分。后者可以适应 POST 等应用需求，但要自己处理解析、取消和重连策略；不能因为响应格式叫 SSE，就自动拥有原生 EventSource 的全部行为。

背压（Backpressure）处理生产速度超过消费速度的问题。如果模型或上游不断产出，而浏览器渲染很慢，数据会积压在应用、代理或网络缓冲中。系统需要限制缓冲、合并界面更新，并按接口能力暂停读取或取消请求。TCP 的流量控制只约束相应传输链路，不保证模型计算立刻变慢；SSE 本身也没有替应用完成端到端背压。代理缓冲还可能让服务器“边生成边发送”，用户却最后才一次看到。

观察合理判断还不能推断
HTTP 200，随后发生错误响应已开始，后续失败需在流或状态查询中表达整轮对话成功
若干文本增量已显示界面得到了部分内容完整结果已持久保存
收到本应用的完成事件按应用契约解释它承诺了什么任何产品的完成事件都意味着落盘成功
网络连接关闭传输通道结束或中断模型正常结束，或外部任务没有继续

第 02 章 / 06把终态设计清楚：完成、失败、取消和未知

为了让“完成”有清楚含义，本章采用一个设计：先保存完整内容和终态，再向界面发送完成通知。这样界面看到完成，通常就能通过查询恢复内容。但如果落盘成功后通知丢失，浏览器仍会不确定，应该按 turn_id 查询状态，而不是重跑模型生成。

这不是所有产品现状。有的应用先显示完成、后异步保存，体验延迟可能更短，却存在“看见成功但刷新消失”的窗口。选择哪种顺序要明确承诺，并为窗口内失败准备行为。

取消请求 ≠ 取消完成

点击停止先改变用户意图，再发送取消，应用还要向模型或工具传播。上游可能已经完成，或无法撤回副作用，所以取消状态需要结果确认。

连接丢失 ≠ 执行失败

客户端不知道结果时应标成“连接中断，正在确认状态”等可解释状态。后台可能成功、失败或仍在运行，查证后再归类。

部分回答如何进入下一轮历史也要有政策：排除它、标为未完成，或经过确认后保留。不能把被截断的“明天可安排在……”当成完整结论。用户提交通常可以保留；助手部分内容须带来源、所属轮次和终态，避免后续误用。

第 02 章 / 07状态由谁保存：刷新、重启与恢复分别发生什么

位置适合保存典型生命周期不能独自保证
浏览器内存草稿、加载状态、当前显示片段页面刷新后通常消失跨设备同步、可靠执行状态
浏览器持久存储本地阅读偏好或草稿缓存依浏览器、清理和隐私设置服务端真相、其他设备可见
应用进程内存活动请求、连接、临时取消句柄进程重启后消失重启后继续生成或工具执行
持久数据库 / 文件消息、轮次状态、请求引用、终态依实际存储位置与持久化配置自动重建进程、网络连接和调度
模型服务侧状态托管会话或计算缓存，若接口提供依供应商契约应用自己的授权、任务正本与完整审计

正本（Source of truth）是系统判断某类事实时采用的权威记录。消息正本可在数据库，界面是它的呈现；执行状态正本也需要明确。正本是设计责任，不由文件扩展名自动决定。SQLite 是数据库实现，数据文件放在易丢失的位置仍会丢失；“用了数据库”不等于有备份或可靠存储。

数据库事务能把相关写入作为一个提交单元，例如最终消息与轮次终态一起更新；SQLite 的原子提交说明解释了其本地提交机制。它不把远程模型调用和界面通知也变成同一数据库事务。把耗时模型调用夹在长事务中还可能增加锁占用，通常应把短时状态提交和远程等待分开设计。

第 02 章 / 08重试与并发：为什么成功路径之外需要边界

策略收益代价 / 适用条件
忙时拒绝状态简单，避免相互覆盖用户需等待或重试，要说明未受理
按会话排队保持明确先后关系排队会增加延迟；执行前需确定使用哪版历史
允许并行分支支持比较或独立探索要显示分支关系，不能把结果随意拼成线性历史

重试需要先判断失败发生在哪。发送前参数错误，应修正输入；明确限流可按规则等待；已经收到部分文本后直接把第二次结果接在后面，会拼成两次不同生成的混合答案。每次尝试必须有自己的身份，旧片段要明确丢弃、保留为中断稿，或使用服务真实支持的续传机制。

幂等（Idempotency）关注重复请求是否造成重复业务效果。稳定提交标识可以帮助应用避免重复创建同一轮，但不代表供应商一定不会重复计费，也不意味着模型两次生成逐字一致。HTTP 对安全方法和幂等语义的定义见 RFC 9110 §9.2；业务仍要明确自己的去重范围和结果保留策略。

本章只要求你能识别“未知是否已受理”和“已有部分输出”这两种重试风险。第 03 章会加入外部动作，届时重复创建日程会比重复生成文字更严重；可靠事务协调放到第 09 章。

第 02 章 / 09可观测性：用一条 Trace 解释这次发生了什么

Trace关联一次处理中的操作，Span描述其中一个有起止时间的操作。OpenTelemetry规定了相关概念与上下文传播。追踪不是“保存模型全部思维”：它主要记录可观察的输入、调用、结果、状态和时间。

信号适合回答例子
Logs · 日志某个事件发生了什么会话访问检查未通过、请求被限流
Traces · 链路追踪这一轮时间和失败分布在哪历史读取 20ms，模型等待 1800ms，保存 15ms
Metrics · 指标一段时间内总体怎样错误率、延迟分位数、队列长度、用量趋势

上述耗时是教学数值，不能当实测。TTFT（Time to First Token）要说明计时边界：服务侧首 Token、应用侧首内容片段、用户看到首段文字并不相同。如果前端测不到 Token，只应命名为“首内容到达时间”或“首可见输出时间”，避免把网络等待、缓冲和渲染都误算成模型计算。

时间怎么拆

总响应时间包含排队、历史读取、输入处理、生成、传输和提交，部分阶段可能重叠。浏览器和服务器的绝对时钟也可能有偏差，跨机器统计要有统一策略。

Token 与费用怎么记

以接口实际报告的 usage 为主要依据，区分输入、输出与缓存等计费类别。重试可能产生额外费用；不要用 SSE 事件数推算 Token，未报告的数据应记为未知。

生产 Trace 可能含私有笔记、用户问题和工具输出。需要访问控制、脱敏和保留期限。若为降低成本采用采样，某轮没有 Trace 也不等于没有执行过；关键业务结果仍应有可靠状态记录。

第 02 章 / 10完整案例：界面没有答案，怎样逐层定位

可观察现象首先找的证据可能的结论 / 后续判断
点击后一直“发送中”浏览器是否建立请求；服务端是否记录提交标识区分未到达、已受理但响应丢失；先确认状态，避免重复提交
立刻收到访问错误会话存在检查与归属检查是访问边界问题，尚未进入模型生成
服务端有内容，界面一直空白流首片段时间、代理缓冲、客户端解析可能在传输或消费端；不能只责怪模型慢
显示半句话后中断该轮终态、结束原因、原始事件类型可能是输出限制、连接问题或取消；部分文本不当作完整答案
界面显示成功，刷新后没有结果提交记录、完成通知顺序、读取会话是否相同检查保存失败、读取错会话或异步提交窗口
完整回答却引用不存在的 N2实际输入与引用映射数据组装或生成依据问题；网络正常不能证明语义正确

一次排障只改变一个条件。例如 B1 只移除 N2：模型、问题、其他资料与设置保持一致。否则答案变化可能来自多个原因，难以解释。对话追踪的价值是把“我感觉模型忘了”转成可检查的问题：本轮是否真的收到 N2？引用是否支持结论？

本章构建的是观察框架，并没有声称已运行这些生产故障。深度来自能区分因果和证据，而不是把每一种现象都列成一个新的功能。

第 02 章 / 11总结、自述与面试 FAQ

先用自己的话解释：收到 20 次 delta 与收到完成事件，各能证明什么？页面刷新能恢复消息，为什么还不能证明任务能继续执行？下面的答案集中回顾本章，不要求记住某套框架的字段。

1. 一轮对话就是一次 HTTP 请求、一次模型调用吗？

不一定。一个提交可能触发创建会话、调用模型、查询状态等请求；一次逻辑模型调用又可能有多次尝试。到 Agent 阶段，一轮响应还可能包含工具调用和后续模型调用。因此 Session、Turn、逻辑调用与 Attempt 应分开关联。

2. 前端已经有 session_id，后端还查什么？

仍需确认会话存在、属于当前身份且允许访问，再读取历史。前端的 ID 只决定能否跳过创建会话。新会话通常也查历史，只是查到空集合；检查会话存在和查询消息是两个操作。

3. 20 次 delta 就是 20 个 Token 吗？done 呢？

不是。delta 是应用定义的增量事件，一次可能含多个 Token 的文本，网络还可能拆分或合并事件。done 的含义由协议约定：它可能仅表示生成结束，也可能在本应用中表示结果已提交；不能单凭事件名字推断落盘或业务完成。Token 用量要看接口报告。

4. 为什么断线以后不能直接重试？

服务端可能已接受并仍在执行，或者已经完成但回包丢失。直接重试可能重复计费、重复消息，后续工具阶段还会重复副作用。我会先按稳定标识查询状态；需要重新尝试时建立新 Attempt，并明确处理之前的部分输出。

5. 聊天记录存进 SQLite，为什么不能自动恢复运行？

数据库保存了记录，但活动网络连接、进程内执行位置和取消句柄不会自动恢复。恢复展示只需读到已存内容；恢复执行还需要检查点、任务调度和对外部结果的核对。这是两种不同能力。

6. Trace 记录了什么，不记录什么？

我会记录这轮请求的相关操作、各阶段耗时、输入版本和快照引用、模型与工具调用结果以及终态。它解释系统的可观察行为，不等于模型的完整内部思维，也不能把含密钥或私有资料的全文无权限地开放。

7. 模拟生产面试：模型端已经输出，用户却迟迟看不到，怎么查？

【生产场景模拟】我会比较模型首内容、应用收到首片段和浏览器显示首片段的时间。若应用很快收到而浏览器很晚，查代理缓冲、传输及前端消费；若应用也很晚，则继续查排队和上游。指标的起止边界要一致，不能把所有延迟归到模型。

8. 模拟生产面试：如何避免两个标签页把会话弄乱？

【生产场景模拟】我会先定义并发语义。普通线性对话可按会话排队，或忙时拒绝；如果允许并行，就明确创建分支。受理和历史版本选择应在服务端协调，界面禁用按钮只是体验措施，不能代替服务端并发控制。
